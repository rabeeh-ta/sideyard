Why Sideyard exists

Building got fast. Hosting didn't.

A coding agent builds an app in an afternoon. Then it needs a home, and every new project means picking a host, a managed database, a cache, a cron service, an email provider and a file store. Each has its own account, its own setup and its own bill. So most side projects stay on a laptop, or quietly die on a free tier.

One VPS Sideyard + your apps

Sideyard fixes the stack instead of the hosting. When every app is Go + React + SQLite, every app is one small binary, and one server runs all of them. The database, jobs, email, files and backups are built into the platform, so there's nothing else to sign up for.

How to build from here on

One stack. On purpose.

Every app uses the same four pieces. Fixing the stack is what keeps apps tiny, makes deploys boring, and lets the dashboard understand each app's database, jobs and files instead of just running a container.

GoThe API, background work and WebSockets, in one process
ReactTypeScript and Vite, embedded in the binary
SQLiteOne file in the app's data folder, pure-Go driver
S3Uploads and big files, in a bucket you bring

No Docker. No Postgres. No Redis. No Node at runtime.

Why it pays off

Small, boring and yours.

Tens of MB per app.

An app is one binary that idles at tens of megabytes, so a 4 GB VPS has room for plenty. One server bill covers every side project.

A bad deploy can't take you down.

A new release gets traffic only after it answers /healthz. If it fails, the old one keeps serving.

Your agent knows the rules.

Every app carries its contract in AGENTS.md, so Claude Code, Cursor or Codex builds features that deploy on the first push instead of reaching for services your server can't run.

Your server. Your data.

Databases are files you can see, backups land in your own bucket, and apps are plain Go programs. No lock-in.

What's in it today

Everything a side project needs. Already built.

One dashboard for every app, and one binary for the whole platform, with Caddy built in.

Push to deploy

A GitHub Action builds one binary and uploads it. Traffic moves only after the health check passes.

Instant rollback

The last five releases stay on disk. Rolling back starts an older one, with no downtime.

HTTPS domains

A subdomain for every app, plus custom domains. Certificates are issued and renewed for you.

Isolated apps

Each app runs as its own user with memory and CPU limits, and can write only its own folder.

Table and SQL editor

Browse and edit rows, change structure, run SQL, download a snapshot or import a database.

Backups

Every database is snapshotted to your S3 bucket on a schedule. Restore one from the dashboard.

Cron jobs

Schedules, retries and run history. A job is just an HTTP endpoint in your app.

Email

Send through any SMTP provider with one API call. Every app gets a sender and a delivery log.

File storage

Connect a bucket per app and browse its files. Credentials reach the app as variables.

Encrypted variables

Config and secrets are sealed at rest and never shown again once saved.

Logs and monitoring

Searchable logs, CPU and memory per app, server health, and a flag in the dashboard when an app goes down.

One-click updates

Installs with one command. Updates install from the dashboard and roll back if they fail to start.

How it works

Prompt. Push. Live.

Building the app is your agent's job. Running it is Sideyard's.

  1. Start from a prompt

    Paste the new-app prompt into your coding agent. It sets up the starter, saves the contract as AGENTS.md and builds what you describe.

  2. Create a project

    Add the project in the Sideyard dashboard and put its deploy token in your GitHub repo. The app gets its own subdomain with HTTPS.

  3. Push

    CI builds one Linux binary with the frontend inside and uploads it. Sideyard starts it, checks its health, then switches traffic.

Prompts

Paste one into your coding agent.

Each prompt carries the full Sideyard contract and the starter's code, so it works in any agent with nothing to download. Paste it as your first message and the app comes out ready to host.

Starting something new

Open your agent in an empty folder, paste this first, and write what you want to build in its last section. The agent:

  1. Creates the starter: Go server, SQLite migrations, jobs, email, React frontend and deploy workflow.
  2. Saves the contract as AGENTS.md, so every later session keeps to it.
  3. Checks that it builds and answers /healthz.
  4. Builds your app inside the stack, then tells you how to deploy it.

Moving an app you have

Paste this in your current project. Nothing changes until you approve a plan, and your running app and its database are never touched. The agent:

  1. Audits the app and writes SIDEYARD_MIGRATION.md: every service mapped to its Sideyard equivalent, every route, every table. Then it waits for you.
  2. Ports the backend to Go route by route, keeping the API's shape, and the schema to SQLite.
  3. Copies your data with a re-runnable exporter and checks row counts and integrity.
  4. Writes the cutover steps, with a rollback that's just pointing DNS back.

Trade-offs

What you give up, honestly.

Sideyard is for the many small apps you build, not the one that needs a cluster. These limits are choices, and they're what keep it light.

Out of scope, permanently

  • Other databases. No Postgres, MySQL or Redis. SQLite handles more than most apps need.
  • Other runtimes. No Node, Python or Ruby servers, and no Docker.
  • Scale-out. No Kubernetes, autoscaling or GPUs. One server, sized by you.

Limits to know today

  • Backups are snapshots. Every 6 hours by default, so a dead server can lose up to one interval.
  • Migrations don't roll back. Each one must work with the previous release's code.
  • One admin. A single password-protected user, and alerts show only in the dashboard for now.
Install

One command on a fresh server.

Point *.example.com at an Ubuntu or Debian server, then run:

curl -fsSL https://github.com/rabeeh-ta/sideyard/releases/latest/download/install.sh | sudo bash

It asks for your domain, an email for Let's Encrypt and an admin password, starts Sideyard as a systemd service and prints the dashboard's address. New versions install from the dashboard with one click, or automatically.
