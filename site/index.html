Why Sideyard exists

Building got fast. Hosting didn't.

You can vibe-code an app in an afternoon now. Then it needs a home, and every app means picking a host, a managed database, a cache, a cron service, an email provider and a file store, each with its own account, setup and bill. So most vibe-coded apps never leave localhost, or quietly die on a free tier.

How to build from here on

Your agent writes the code. Let it use one stack.

Left alone, agents reach for a different stack every time: Next.js here, Postgres there, a queue somewhere else, and each needs its own hosting. On Sideyard every app uses the same four pieces. Your agent doesn't mind, and each app comes out as one small file, so one server holds plenty of them.

GoThe API, background work and WebSockets, in one process
ReactTypeScript and Vite, embedded in the binary
SQLiteOne file in the app's data folder, pure-Go driver
S3Uploads and big files, in a bucket you bring

No Docker. No Postgres. No Redis. No Node at runtime.

What's in it today

Everything your apps need. Already built.

One dashboard for every app you've built, and one binary for the whole platform.

Push to deploy

A GitHub Action builds one binary and uploads it. Traffic moves only after the health check passes.

Instant rollback

The last five releases stay on disk. Rolling back starts an older one, with no downtime.

HTTPS domains

A subdomain for every app, plus custom domains. Certificates are issued and renewed for you.

Isolated apps

Each app runs as its own user with memory and CPU limits, and can write only its own folder.

Table and SQL editor

Browse and edit rows, change structure, run SQL, download a snapshot or import a database.

Backups

Every database is snapshotted to your S3 bucket on a schedule. Restore one from the dashboard.

Cron jobs

Schedules, retries and run history. A job is just an HTTP endpoint in your app.

Email

Send through any SMTP provider with one API call. Every app gets a sender and a delivery log.

File storage

Connect a bucket per app and browse its files. Credentials reach the app as variables.

Encrypted variables

Config and secrets are sealed at rest and never shown again once saved.

Logs and monitoring

Searchable logs, CPU and memory per app, server health, and a flag in the dashboard when an app goes down.

One-click updates

Installs with one command. Updates install from the dashboard and roll back if they fail to start.

Moving an app you have

Paste this in your current project. Nothing changes until you approve a plan, and your running app and its database are never touched. The agent:

  1. Audits the app and writes SIDEYARD_MIGRATION.md: every service mapped to its Sideyard equivalent, every route, every table. Then it waits for you.
  2. Ports the backend to Go route by route, keeping the API's shape, and the schema to SQLite.
  3. Copies your data with a re-runnable exporter and checks row counts and integrity.
  4. Writes the cutover steps, with a rollback that's just pointing DNS back.

Trade-offs

What you give up, honestly.

Sideyard is for the many small apps you build, not the one that needs a cluster. These limits are choices, and they're what keep it light.

Out of scope, permanently

  • Other databases. No Postgres, MySQL or Redis. SQLite handles more than most apps need.
  • Other runtimes. No Node, Python or Ruby servers, and no Docker.
  • Scale-out. No Kubernetes, autoscaling or GPUs. One server, sized by you.

Limits to know today

  • Backups are snapshots. Every 6 hours by default, so a dead server can lose up to one interval.
  • Migrations don't roll back. Each one must work with the previous release's code.
  • One admin. A single password-protected user, and alerts show only in the dashboard for now.

Install

One command on a fresh server.

Point *.example.com at an Ubuntu or Debian server, then run:

curl -fsSL https://github.com/rabeeh-ta/sideyard/releases/latest/download/install.sh | sudo bash

It asks for your domain (or offers a free sslip.io name) and an admin password, starts Sideyard as a systemd service and prints the dashboard's address. New versions install from the dashboard with one click, or automatically.
